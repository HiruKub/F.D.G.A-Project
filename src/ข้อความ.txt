================================================================================
          FPGA CAMERA-BASED MONSTER BATTLE SYSTEM ARCHITECTURE PLAN
                          (EDGE Spartan-7 Dual Board)
================================================================================

1. ภาพรวมโปรเจกต์ (PROJECT OVERVIEW)
--------------------------------------------------------------------------------
โปรเจกต์นี้เป็นการพัฒนาระบบเกมต่อสู้มอนสเตอร์โต้ตอบ Real-Time บนบอร์ด EDGE Spartan 7 
จำนวน 2 บอร์ด โดยอาศัยการประมวลผลภาพจากกล้องถ่ายรูปจริงเพื่อสร้างมอนสเตอร์ตามโทนสี 
การประมวลผลกราฟิก VGA การประมวลผลฮิสโตแกรมสีสด และการสื่อสารข้อมูลผ่านโปรโตคอล SPI

แบ่งโครงสร้างการทำงานออกเป็น 2 บอร์ดหลัก (SoC Architecture):

[ FPGA 1: Video, Image Processing & Graphics Hub ]
  - รับภาพจากกล้องความละเอียด 120p (RGB332)
  - คำนวณความถี่สีสูงสุด 2 อันดับแรกด้วย 256-bin Histogram Logic
  - จัดเก็บ Dual-Port Frame Buffer และ Sprite ROM มอนสเตอร์ทั้งหมด
  - วาดภาพรวม (VGA Compositor @ 60Hz) ประกอบด้วย ฉากหลังสด, ตัวละคร 2 ฝั่ง, 
    และ HUD (หลอดเลือด HP, ตัวเลข Level, ข้อความเมนู)

[ FPGA 2: Game Logic Engine & Controller ]
  - ประมวลผลกฎเกณฑ์กติกาเกม (Finite State Machine - FSM)
  - รับสัญญาณปุ่มกด 3 ปุ่ม (Select / Attack / Run)
  - คำนวณความสัมพันธ์แพ้-ชนะธาตุ (RGB), ค่าความเสียหาย (Damage), และโอกาสจับมอนสเตอร์
  - สื่อสารส่งผ่านแพ็กเกจข้อมูลสถานะกลับไปควบคุมกราฟิกบน FPGA 1 ผ่าน SPI


2. การวิเคราะห์การใช้หน่วยความจำ BLOCK RAM (BRAM ANALYSIS ON FPGA 1)
--------------------------------------------------------------------------------
ชิป FPGA: Xilinx Spartan-7 (XC7S15)
ความจุ Block RAM ทั้งหมด: 360 Kb = 45.00 KB (10 บล็อก x 36 Kb)

รายการจัดสรรหน่วยความจำ BRAM:
┌───────────────────────────┬──────────────────────────────────┬──────────────┐
│ รายการใช้งาน               │ รายละเอียดขนาดข้อมูล              │ ความจุ BRAM  │
├───────────────────────────┼──────────────────────────────────┼──────────────┤
│ 1. Camera Frame Buffer    │ 160 x 120 พิกเซล (RGB332 8-bit)  │    18.75 KB  │
│ 2. Monster Sprite ROM     │ 3 ตัวละคร x 6 ท่า (32x32 4-bit)  │     9.00 KB  │
│ 3. Font ROM (HUD Logic)   │ 64 อักขระ x 8 ไบต์ (8x8 Font)     │     0.50 KB  │
│ 4. Color Histogram Buffer │ 256 บ็อกซ์ x 2 ไบต์ (RGB332 Bins) │     0.50 KB  │
├───────────────────────────┴──────────────────────────────────┼──────────────┤
│ รวมหน่วยความจำ BRAM ที่ใช้ทั้งหมด                              │    28.75 KB  │
│ ความจุ Block RAM รวมคงเหลือบนชิป                              │    16.25 KB  │
└──────────────────────────────────────────────────────────────┴──────────────┘

* สรุปเปอร์เซ็นต์การใช้งาน BRAM: 63.88% (เหลือพื้นที่ปลอดภัยอีก 36.12% 
  ช่วยให้การ Synthesis & Place-and-Route ใน Vivado ทำได้รวดเร็วและไม่มีปัญหา BRAM เต็ม)


3. จุดแข็งของโปรเจกต์ (PROJECT STRENGTHS)
--------------------------------------------------------------------------------
[+] Full-Stack System-on-Chip (SoC) Integration:
    แสดงถึงทักษะการรวมเซนเซอร์ (กล้อง), การประมวลผลฮาร์ดแวร์ Real-Time (Histogram),
    การสร้างสัญญาณแสดงผล (VGA Compositor) และการสื่อสารข้ามชิป (SPI)
[+] Real-World Interactive Gaming:
    การดึงสเปกตรัมสีจากโลกจริงผ่านกล้องมาสุ่มสเตตัสมอนสเตอร์ สร้างความน่าสนใจและความสนุก
    ในการสาธิตโปรเจกต์ (Wow Factor)
[+] Zero SPI Bottleneck Architecture:
    ย้ายการเก็บไฟล์ภาพกราฟิกทั้งหมดมาไว้ที่ FPGA 1 แล้วส่งผ่าน SPI เฉพาะข้อมูลเมทาดาต้าสั้นๆ
    (4-6 ไบต์) ทำให้ระบบแสดงผลกราฟิกได้ลื่นไหล 60 FPS ปราศจากความล่าช้า (Latency)
[+] All-in-One VGA Interface:
    ย้าย HUD (หลอด HP, เลเวล, ข้อความ) ขึ้นไปวาดรวมบน VGA ทำให้ระบบดูเป็นเกมอาร์เคดสมบูรณ์แบบ
    และลดสายสัญญาณรบกวนจากการไม่ใช้จอ LCD/7-Segment ภายนอก
[+] Multi-Clock Domain Mastery:
    มีการจัดการ Clock Domain Crossing (CDC) อย่างเป็นระบบ ทั้ง Pixel Clock (25MHz), 
    Camera PCLK, SPI Clock และ System Clock ผ่าน Dual-Port RAM และ Synchronizers


4. จุดอ่อน ข้อควรระวัง และแนวทางแก้ไข (RISKS & MITIGATIONS)
--------------------------------------------------------------------------------
[!] สภาพแสงภายนอกส่งผลต่อการตรวจจับสีมอนสเตอร์
    - ความเสี่ยง: แสงในห้องพรีเซนต์อาจทำให้สีเปลี่ยนไปจากที่คาดการณ์ไว้
    - แนวทางแก้ไข: กำหนดพื้นที่สแกนเฉพาะ "กรอบกึ่งกลางภาพ" ขนาด 64x64 พิกเซล 
      และทำ Color Thresholding หรือปรับความไวของสีในฮิสโตแกรม

[!] สภาวะ Metastability จากการส่งข้อมูลข้าม Clock Domains
    - ความเสี่ยง: สัญญาณควบคุมจาก SPI หรือปุ่มกดอาจเกิด glitch เมื่อเข้าสู่ Clock 25MHz
    - แนวทางแก้ไข: ใช้ Double Flip-Flop Synchronizers สำหรับสัญญาณปุ่มกดและสาย SPI 
      และใช้ Dual-Port RAM สำหรับข้อมูลวิดีโอจากกล้อง

[!] ความล่าช้าจากการคำนวณตำแหน่งพิกเซล (VGA Timing Glitches)
    - ความเสี่ยง: การซ้อนเลเยอร์ (Layering) หลายชั้นอาจทำให้การเปรียบเทียบพิกเซลไม่ทันจังหวะ
    - แนวทางแก้ไข: ทำ Registering output ที่ MUX เลเยอร์กราฟิก และคำนวณตำแหน่งล่วงหน้า 1 Clock


5. แผนการดำเนินงานเป็นขั้นตอน (IMPLEMENTATION ROADMAP)
--------------------------------------------------------------------------------
ระยะที่ 1: VGA Core & Sprite Engine (FPGA 1)
  - เขียนและทดสอบ VGA Controller (640x480 @ 60Hz, 25MHz)
  - เขียน Sprite ROM และวาดตัวละครขนาด 32x32 แบบเปลี่ยนท่าทางขยับนิ่ง (Idle)
  - เขียน Layer Compositor ซ้อนตัวละคร 2 ฝั่งพร้อมกำหนดระบบสีโปร่งใส (Color Key)

ระยะที่ 2: Camera & Frame Buffer (FPGA 1)
  - เขียนตรรกะรับสัญญาณภาพจากกล้องลง Dual-Port RAM (160x120 RGB332)
  - นำภาพถ่ายจาก RAM มายืดแสดงผลเป็นฉากหลังเต็มจอ VGA
  - ทำระบบ Freeze Frame (Snapshot) เมื่อกดปุ่มถ่ายภาพ

ระยะที่ 3: Color Histogram Analysis Logic (FPGA 1)
  - เขียนวงจรสแกนพิกเซลกลางภาพ และนับความถี่สีลง Histogram RAM (256 Bins)
  - เขียน State Machine ค้นหาค่าสีสูงสุดอันดับ 1 และ 2 เพื่อแปลงเป็นธาตุและเลเวล

ระยะที่ 4: Game Logic & FSM (FPGA 2)
  - ออกแบบ FSM ควบคุมสถานะเกม (Select -> Battle -> Damage Calc -> Result)
  - ทำการคำนวณ HP, DMG, การแพ้/ชนะธาตุ และระบบจับมอนสเตอร์ตามปุ่มกด 3 ปุ่ม

ระยะที่ 5: SPI Bus & Full Integration (FPGA 1 <-> FPGA 2)
  - เชื่อมต่อโปรโตคอล SPI แบบ 4-wire ระหว่างบอร์ด
  - ทดสอบการส่ง Color Data จาก FPGA 1 -> FPGA 2 และส่ง Status Update กลับ
  - วาด HUD (Health Bar, Level, Menu Text) ซ้อนทับบน VGA
  - ทดสอบและปรับแต่งสมดุลระบบโดยรวม
